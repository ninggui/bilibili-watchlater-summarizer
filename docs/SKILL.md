# B站稍后再看视频总结

把越积越多的「稍后再看」变成一份"先看哪条、哪些可跳过"的摘要文档。
设计目标不是体积小，而是**决策一次走对，不为白转写、白总结、二次返工消耗 token 与时间**。

## 核心设计：分类路由 + 自我纠错（零走弯路）

每条视频在**花任何转写/模型成本之前**，先用零成本信号（分区、时长、标题、字幕轨）决定走哪条解析路径：

| 路由 route | 触发条件 | 处理方式 |
|---|---|---|
| `subtitle` | wbi 字幕质量分级为 good | 直接用字幕（长视频用带时间戳版） |
| `transcribe` | 无可用字幕 | **走飞书妙记转写**——下载音频→上传妙记→等待AI摘要→整理成总结。实测投入产出比高：妙记本身不耗token，模型只需处理摘要文本（约¥0.001-0.002/条），质量好 |
| `card_meta` | 手工/生活短视频、标题含"纯享/声浪/ASMR/试听"或"花艺/风光/治愈/城市漫步"等纯视觉无口播信号、互动极低 | 只用标题+简介出卡片；花艺/风光类在总结里一句话带过 |
| `skip_music` | 音乐/舞蹈/演奏/音MAD 分区，或字幕全是 ♪ | 直接跳过 |
| `skip_short` | <30s 且无字幕 | 跳过/卡片 |
| `error` | 拉取失败 | 单条隔离，不影响其它视频 |

**自我纠错闭环**：
- 字幕串台/残缺 → wbi 签名 + 时间覆盖/语速双校验，不合格自动换字幕轨，仍不合格走妙记转写；
- 无字幕 → 直接走飞书妙记转写（实测投入产出比高：token消耗极低，质量好）；
- 妙记 `not ready` → 自动轮询直到AI摘要就绪；
- 妙记转写后判定无人声 → 回退卡片/跳过；
- 转写每条完成立即落盘，中断后重跑自动跳过已完成（断点续转）。

## 完整工作流

### 第 1 步：取数 + 分流（秒级，不花模型 token）

```bash
python3 scripts/bili_digest.py --limit 10 --json output/summaries/digest.json
```

输出每条视频的 `route`、`route_reason`、字幕质量（good/sparse/bad/none/music）、
分区、分 P、弹幕高能点；结尾直接打印"需要妙记转写"的清单。

### 第 2 步：对高价值无字幕视频自动转写（仅豆包/飞书环境）

```bash
python3 scripts/transcribe_fallback.py --digest output/summaries/digest.json
# 可选：--limit N 限量、--poll 20 --interval 30 调轮询、--force 强制重转
```

- 自动发现 `doubao-video-extract` skill（也可用环境变量 `VIDEO_EXTRACT_SKILL` 指定目录）；
- 下载→转 MP3→上传妙记→轮询→把**结构化摘要**回填到 JSON 的 `minutes` 字段；
- 跨平台/无飞书环境此步不可用，可改用本地 Whisper，把结果填进同样的 `minutes.summary` 字段，后续流程不变。

### 第 3 步：AI 生成总结

把 digest JSON 交给 AI，加载 `prompts/summary_prompt_final.md`。取数原则：
- `subtitle`：用 `subtitle`；时长>10min 用 `subtitle_timed`（含 30 秒锚点时间戳）；
- `transcribe`：用 `minutes.summary`（妙记已结构化，不要再喂逐字稿，省 token）；
- `card_meta`：用标题+简介+弹幕，明确标注信息有限；
- `skip_*`：一句话带过。

输出：决策速览表（**严格按稍后再看原序**，不按密度重排）→ 正文按原序号逐条成节 → 多P标注/同主题软引用不挪位 → 弹幕仅知识/观点类展示 → 纯配乐花艺风光类一句话带过。

### 第 4 步：写入飞书

```bash
lark-cli docs +create --doc-format markdown \
  --title "B站稍后再看视频摘要（日期）" \
  --content "@./output/summaries/final.md" --as user
```

## 关键技术点

- **wbi 签名**：未签名的 `x/player/v2` 会返回串台字幕（53 秒视频配 8 分钟别的视频字幕）。
  必须用 `x/player/wbi/v2` 签名，并校验：字幕时间覆盖 0.7~1.3 倍视频时长、语速 0.5~8 字/秒。
- **标题-BV一致性校验**：获取字幕后，先用API返回的视频标题与稍后再看列表中的标题做模糊匹配（去标点后包含关系），不一致则标记 `mismatch` 跳过，防止BV错配导致总结串台。批量补BV号后，必须抽样验证3-5个视频的标题-BV是否匹配。
- **字幕内容相关性校验**：拉取字幕正文后，取前200字与标题做关键词重叠校验（至少1个≥4字的关键词或标题核心名词出现在字幕前200字）。不相关 → 标记 `subtitle_mismatch`（AI字幕串台），不得用错字幕生成总结，统一标记"⏳ AI字幕串台不可用，待妙记转写后补全总结"，并在后续转写批次处理。
- **禁止重复标记**：每个视频段落内，同类型状态标记（⚠️未匹配BV / ⏳待转写 / ⚪纯视觉）只允许出现一次。插入标记前先检查段落内是否已存在；若已存在则跳过。禁止在已有BV链接的段落再插入"未匹配BV"警告。
- **字幕完整获取**：不设行数上限，获取完整字幕再总结；短字幕（<100字）自动判定为音乐/纯视觉类。
- **数量词完整性校验**：标题含"N款/N个/N集/N大/N全"时，总结必须覆盖至少N个独立要点；不足时标记 `incomplete` 并提醒人工检查。
- **信息差/新闻类完整性校验**：标题含"信息差/一觉醒来/今日要点/新闻联播"时，总结必须列出全部条目（逐条编号），不得只列前3条就停；字幕中出现"第N/第N条/N."时必须全部提取。
- **BV链接必填**：每条总结末尾必须附BV链接；生成时直接从API记录BV号，**不依赖事后标题匹配**。如果标题被改写过导致匹配失败，必须用关键词提取（去掉修饰词，保留核心名词动词）二次匹配；仍失败时用**B站搜索API兜底**（`/x/web-interface/search/type?search_type=video`）按标题关键词搜索，取第一条结果校验标题一致后作为BV；搜索仍失败才标记 `no_link`（"⚠️ 未匹配到BV号，需手动补全"）。
- **元信息必填（随正文一次写入，禁止事后补）**：每条总结的 checkbox 之后必须紧接 `<p><em>UP主 · 时长 · 分区</em></p>` 元信息行，与BV链接一同在**生成总结的同一批次写入**，禁止"先出正文、事后批量补BV/元信息"（历史遗留 232 条缺BV+233 条缺元信息即因此产生）。全量检核时，缺BV链接或缺元信息的段落一律判为不合格，必须当批修复。
- **禁止占位符BV**：严禁在BV链接处写入 `BV1xxx` 之类占位符（历史遗留 253 处即因此产生，且占位符会被审计误判为有效链接）。匹配失败的处理只有两条路：① 走B站搜索API兜底取真实BV；② 搜索仍失败才标记 `no_link`。全量检核时，`bilibili.com/video/BV1xxx` 必须判为"缺BV"而非"有BV"。
- **补BV/补内容后正文-标题相关性复核**：任何事后补BV、回填正文、修正错配的动作完成后，必须复核"正文核心对象 ↔ 标题关键词"是否一致（如标题是 BBC 却配台湾夜市正文、标题是 Kimi 却配旅行风光正文均属错配）。复核方法：取正文首个结论句与标题做关键词重叠校验（至少1个核心名词/实体重合），不一致必须重写正文或重新匹配BV，禁止"补了链接但正文串台"的条目残留。
- **待办队列闭环（禁止滞留）**：所有标记"⚠️ 未匹配到BV号"或"⏳ 待妙记转写"的视频，必须同时登记进入对应处理队列（`pending_bv` / `pending_transcribe`），并在后续批次统一消化：补BV成功 → 立即验证字幕 → 可生成总结则生成，无字幕/串台则改标记待转写；转写完成 → 回填正文总结并删除待转写标记。**禁止只打标记不做后续处理**，导致条目长期滞留为空。
- **空内容禁止**：任何视频段落（checkbox 到下一个 hr 之间）不得只有 checkbox+元信息+状态标记而无正文。全量检核时，若发现"仅标记无正文"条目，必须按上述队列闭环处理（补BV/验证字幕/转写），不得停留在标记状态。段落允许的合法状态只有三种：① 有正文总结（含BV链接）；② 有正文总结+待转写标记（转写后补全正文）；③ 纯视觉/音乐类一句话带过（含BV链接）。
- **总结不截断**：长视频（>5分钟）总结后，对比字幕首尾时间戳——如果总结只覆盖了字幕前1/3内容，标记 `truncated` 重新生成。
- **信息密度**：根据视频时长调整总结长度，优先保证质量。长视频（>10分钟）展开为5-8个段落，每个段落讲清一个核心论点；中视频（5-10分钟）3-5段；短视频（<5分钟）3-4句。不要为了省token而牺牲内容深度。
- **选轨**：优先中文原文轨（`ai-zh`、`ai_type=0`），避免选到机翻轨。
- **分区路由**：内置 B站 tid 映射（知识/科技/汽车/美食/音乐/舞蹈…），决定无字幕时是否值得转写。
- **标题信号**：纯享/纯音乐/伴奏/声浪/ASMR/助眠/试听/翻唱，或花艺/插花/风景/风光/治愈/城市漫步/航拍等纯视觉词命中时不主动转写；但标题带"教程/详解/怎么拍/入门"等教学词时视为有口播，仍走转写（避免误伤花艺教程、风光摄影教学）。
- **UP 黑名单跳过（2026-09-25 用户确认）**：纯音乐/纯视觉/无内容类 UP 整体跳过——**不入稍后再看、不总结、不进文档**。名单见 `config/skip_ups.json`（当前 13 位：JLRS-LeoFM、JLRS-jayfm、FM音乐珍藏馆、施利TV、李明娥、老黎和小黎、北京山水民乐艺术团、花之了Flowers_Know_、野生花艺师Fiona、花艺师凡、8KRAW、东韵Dongyun、纯享木匠师Olof）。生效环节：① feed 自动入库（toview/add 前按 up mid 过滤）② toview 拉取分流（命中即跳过/一句话带过）③ 文档总结。判断口径：UP 最近视频全为纯音乐/纯视觉无口播（ASMR/试听/演奏/花艺/风光等），或签名明确纯音乐类；有口播的教程类（远征教插花、九婶的微醺日常）不列入。新增黑名单时更新 `config/skip_ups.json` 并同步 GitHub。
- **弹幕**：仅总量>100 时取 30 秒窗口密度 top3，且只留≥8 字的有信息量弹幕。
- **多 P**：`pages_count>1` 时输出各 P 的 cid/part，可逐 P 取字幕。
- **去重**：`tracker/processed.json` 记录已处理 BVID，定时跑只处理增量。
- **block ID 完整提取**：解析飞书文档 block 时，必须完整提取 `id="..."` 中的完整字符串（约27字符），禁止截断；否则删除操作会因 ID 不匹配而静默失败。
- **勾选删除=整段删除**：用户勾选 todo 后，必须删除从 checkbox 到下一个 `<hr/>` 之间的所有 block（p/ul/li），不能只删 checkbox block 本身——否则会留下无 todo 的残留内容。
- **删除后验证**：批量删除后重新 fetch 文档，确认 checkbox 数量和内容一致；发现"有内容无 checkbox"的孤儿段立即清理。
- **分隔线清理**：删除视频段落后，必须同时删除对应的 `<hr/>` 分隔线；清理后检查是否有连续两个 hr 或 h2 后紧跟 hr 的情况，有则删除多余的 hr。
- **章节标题同步**：删除已看完的视频后，必须更新对应 h2 章节标题的序号范围。例如删除前20条后，章节标题从"第1–50条"改为"第21–50条"；如果第一个视频不是第1条，标题从实际起始条号开始。删除前先 fetch outline 确认每个分区的实际编号 min-max，再统一改写 h2（含部分删除后分区内部编号不连续的情况，标题写实际 min–max）。
- **em 元信息必须带博主名**：`<p><em>频道/UP主 · 时长 · 分区　博主名</em>　</p>`——后半段"　博主名"为用户要求的分类标注，博主名必须与 BV 真实 owner 一致，禁止留空或写"ERR"。批量修复 em 时，用 titles.json 的 owner 字段逐条对齐。
- **链接-标题逐条对齐校验（防系统性错位）**：批量写链接后，必须做全量错位审计——用每条的 checkbox 标题与 BV 真实标题（`x/web-interface/view`）做相似度对比（SequenceMatcher，阈值 0.25 + 主干包含命中）。曾发生整段 696–716"链接滞后一条"的系统性错位（每条链接指向前一条视频的真实 BV），仅凭抽查无法发现。审计发现相邻编号的标题与 BV 成对互换/平移时，按"文档标题 = 正确 BV 真实标题"的反向映射批量修复；修复后重跑全量审计至 0 残留。
- **标题变体不误报**：同视频 UP 主改标题（如"万字深读《边缘日记》" vs "真正的救赎…高分电影《边缘日记》"）会被相似度误报为错位，人工确认两标题共享核心实体（书名/主角名/BV 一致）后判为"标题变体非错位"，无需修改。
- **失效视频链接**：toview 拉取与标题 API 返回 `-404`（视频失效）时，说明该 BV 为旧错误链接（对应视频已删除），必须从 toview 重新按标题关键词匹配真实 BV，不得保留 -404 链接。
- **妙记转写完成即回填**：妙记 `not ready` 轮询成功后（transcript.txt 生成），必须立即生成详写总结并 block_replace 回填正文，替换"⚠️ 妙记转录无有效内容"等占位；占位符段落不得长期滞留。
- **短视频一句话带过**：纯音乐（如"黄昏一响青春散场"）、花艺（如"三种花材插好一份周花"）、沙雕广告（<2min 无解说）等按"一句话带过"写正文（"…短视频：…，无实质解说内容。"），不得留空。

## 排版规范与校验

每个视频段落的标准结构（从checkbox到下一个hr）：
```
<checkbox done="false">N. 视频标题</checkbox>
<p><em>UP主 · 时长 · 分区</em></p>
<p>总结正文第1段</p>
<p>总结正文第2段</p>
...
<p>🔗 https://www.bilibili.com/video/BVxxx</p>
<hr/>
```

**每次修改后必须执行排版校验**，发现以下问题立即修复：
1. **无checkbox的孤儿段**：hr后紧跟`<p>`而不是`<checkbox>` → 清理残留
2. **连续hr**：两个`<hr/>`相邻 → 删除多余的
3. **h2后紧跟hr**：章节标题下直接是分隔线 → 删除多余hr
4. **缺失BV链接**：正文末尾没有`🔗`链接 → 补上
5. **元信息缺失**：checkbox后没有`<em>UP主 · 时长 · 分区</em>` → 补上
6. **内容为空**：checkbox和hr之间没有任何正文 → 标记待补
7. **BV错配抽查**：随机抽3-5个视频，验证API返回的标题与文档标题是否一致 → 不一致则重新匹配
8. **总结密度**：长视频（>10分钟）总结应≥3段正文 → 不足则补全

校验方式：修改后fetch对应section，用正则检查block序列是否符合上述标准结构。

## 成本实测（前 10 条 / 总时长 67 分钟）

- 模型：字幕输入约 5k、总结输出约 5k tokens，约 ¥0.01~0.02；
- 路由后只有真正高价值的长知识视频才转写（10 条中仅 2 条），音乐/纯享/十几秒视频不花转写成本；
- 妙记转写免费但每条几分钟，是主要耗时，故用分区+标题前置过滤把转写量降到最低。

## 运行方式

- **手动**：每周一次，`--limit N` 跑新增。
- **定时（可选）**：cron 编排上面 4 步，配合 tracker 做增量；transcribe 步骤支持断点续转。

## 跨平台复用

- `bili_digest.py` 只依赖 `requests`，无模型/飞书依赖，任意环境可跑；
- 换模型（Claude/GPT/本地）只影响第 3 步；换输出（Notion/Obsidian/邮件）只改第 4 步；
- 换账号只换 `BILI_COOKIE`；无飞书时用 Whisper 替代第 2 步并写入 `minutes.summary`。
